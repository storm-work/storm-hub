# Proxy Contracts

Proxies are a **first-class subsystem**, not an implementation detail behind a generic
abstraction. Providers differ in credential grammar, session semantics, rotation mechanism and
failure modes, and those differences are load-bearing. This file documents the contract for
each supported provider. A "universal proxy" abstraction that hides these differences would be
a bug, not a simplification.

---

## Shared model

A `Proxy` row is a **session template, not an IP.** The exit address behind a row changes over
time. This single fact drives most of the design below.

Consequences:
- `is_healthy` is deliberately **not** a selection filter *for a rotating row*. A failed probe
  means "that exit was bad a moment ago", never "this row is bad". Filtering permanently
  discards a good template over a transient IP. (Once cost 639 rows to a misconfigured prober.)
- The only recovery that works for a rotating pool is **rotation** — which the LRU ordering
  provides.
- Health/score are still recorded and still break ties, so a consistently bad row sinks without
  being cut.

### `resource_type` ('rotating' | 'static') — added Phase 3, 2026-08-26 (`DECISIONS.md` D33)
Every `Proxy` row now carries an explicit `resource_type`, defaulting to `'rotating'`. The
"session template, not an IP" model above, and the "`is_healthy` is not a filter" rule, describe
`resource_type='rotating'` specifically. A `'static'` row is the opposite kind of thing — a
genuinely finite, individually-owned resource (one IP, one session) where a failed probe means
THIS resource is bad, not that an exit moved underneath it. `_candidate_query` excludes an
unhealthy `static` row; it does not exclude an unhealthy `rotating` row. **No `static` inventory
exists in this system as of this entry** — every row generated by `scripts/gen_proxy_pool.py` or
imported today is `'rotating'`, so this distinction is currently a no-op in production and takes
effect only once a static/ISP pool is actually procured and imported with `resource_type='static'`
set explicitly. This does not change the "we own none" statement below.

**Enforced at every lease, not only D33's health scoping — Phase 5, 2026-08-26 (`DECISIONS.md` D34).**
D33 only ever *excludes* an unhealthy static row from an otherwise mixed pool; it was never a way to
*require* a lease return one. `lease_proxy`/`_candidate_query` now take an optional `resource_type`
exact-match parameter (`None` by default — every pre-D34 caller unaffected). `_do_launch_worker`'s
initial hold lease and `_handle_proxy_request`'s every subsequent hold-phase rotation both now pass
`resource_type="static"` whenever the resolved `HOLD_SWAP_AFTER_WARMUP` is on — the guarantee "the
post-swap pool is static" now holds for a worker's entire life, not only its first hold-proxy
assignment. No rotating fallback exists at either call site.

### Rotating pools left the database entirely — 2026-09-15 (`DECISIONS.md` D39)
**The inventory statements above are now history for rotating pools.** Migration `ci000droprot`
deleted every `resource_type != 'static'` row (42,600 of them) and their leases. A rotating pool is
no longer a set of rows at all: it is a set of credentials in global settings
(`SOAX_ROTATING_PACKAGE`/`_PASSWORD`, `SOAX_MOBILE_*`, `WEBSHARE_PREFIX`/`_PASSWORD`, plus the three
soax TTLs), out of which `libs/proxies/rotating.py::mint_rotating_url` builds a credential at launch
and `roll_sticky_session` mints a fresh 16-alphanumeric session id on every rotation.

So the current inventory reads the other way round from everything above: **`resource_type='static'`
is now the only kind of row that exists**, and there are still none of them ("we own none", below,
is unchanged and is the *whole* table). Everything the D33/D34 entries describe — the health filter,
the exact-match `resource_type` parameter, the static-hold invariant — is byte-unchanged and is now
the only path through `lease_proxy`.

**One module per provider (2026-09-16).** Each provider now owns a single file under
`libs/proxies/providers/` holding its connection-string format, the credential fields it needs, and
how a session id is written/re-written inside that string. `soax.py` and `webshare.py` are ~70 lines
each; `base.py` states the contract. Adding a provider is: write the module, add it to the registry
in `providers/__init__.py`. Nothing in the Hub or the worker changes, because `roll()`/`read_id()`
dispatch through `providers.for_url()` instead of a hard-coded if/else over both grammars (which is
what `lease.py` used to carry, in the STATIC leasing module, for rotating credentials).

**Credentials live in the environment, not the database.** `{env_prefix}_{FIELD}` -- e.g.
`SOAX_ROTATING_PACKAGE`/`SOAX_ROTATING_PASSWORD`, `SOAX_MOBILE_*`, `WEBSHARE_PREFIX`/`_PASSWORD`.
They are deployment facts and secrets: identical for every booking, changing only when a
subscription changes. They were briefly catalogued as GLOBAL settings and that was wrong twice over
-- a setting is editable from the web dashboard and readable by any DB connection, and because
`apps/hub/config.py` loads `.env` at import, credential resolution consulting ambient `os.environ`
made the TEST SUITE resolve live production credentials (one appeared in a pytest failure message).
Secrets now resolve from the environment only; `resolve_credentials(env=...)` exists so tests are
hermetic.

**Operational knobs stay in the dashboard**, which is the correct half of the split: geo selection,
`PROVIDER_LOGIN_CONCURRENCY`, and the soax TTLs (`SOAX_SESSIONLENGTH`/`BINDTTL`/`IDLETTL`) are
resolved at launch and passed in. The TTL names are deliberately NOT pool-prefixed -- they describe
SOAX's behaviour, not one purchase, so both soax pools share them.

Consequences worth knowing before reading the rest of this file:
- `is_healthy` on a rotating row is not merely "not a filter" any more; there are no rotating rows
  to carry it. The D19 rule survives in code as a guard, not as a live behaviour.
- The Hub never assigns a rotating exit. `_handle_proxy_request` refuses one with
  `proxy_unavailable` rather than minting Hub-side, because a Hub-side mint would restore the
  46–124 s round-trip the change removed.
- The bound on concurrent use is `PROVIDER_LOGIN_CONCURRENCY`, keyed by provider+kind and enforced
  **host-wide across all bookings**. `Proxy.max_sessions` never bounded anything and now has no
  rotating rows to be ignored on.
- `scripts/gen_proxy_pool.py`'s rotating modes still work and are the documented way to recreate the
  deleted rows if D39 is ever reversed.

**`HOLD_SWAP_AFTER_WARMUP` is the sole hold-swap setting — Phase 6, 2026-08-26 (`DECISIONS.md`
D35).** A deprecated spelling, `HOLD_SWAP_AFTER_FOUND`, existed until this entry and was removed
outright, not reconciled — it was never a legitimate second name, and its presence let the Hub-side
launch/rotation gates above drift onto reading it specifically while the worker's own `EngineConfig`
read both spellings OR'd. There is no alias, no fallback, and no compatibility mechanism; setting the
old name at any layer is rejected exactly like any other unrecognized key.

**The worker never locally rolls a static hold identity.** `roll_sticky_session` (D2) is a pure,
grammar-based string transform with no concept of `resource_type`, and the worker cannot be given one
without violating D1 (no DB access). Instead, a plain runtime fact — `hold_proxy_static: bool` —
rides the existing launch payload and the existing `proxy_assigned` bus-command payload
(`resource_type`, alongside `proxy`). `do_swap`'s retry ladder consults this fact, not the DB: a
static hold proxy is never passed to `roll_sticky_session`; the ladder requests a fresh lease through
the Hub instead (which, per the paragraph above, itself enforces `resource_type='static'`).

### Selection order (`_candidate_query`)

Tiered, then LRU within each tier:

| tier | condition | intent |
|---|---|---|
| 0 | `health == "ok"` | proven good |
| 1 | `health IS NULL AND last_used_at IS NOT NULL` | session established, verdict unknown |
| 2 | `health IS NULL AND last_used_at IS NULL` | never established |
| 3 | otherwise | known bad |

`last_used_at` is stamped on **every attempt, not just success**, so a candidate that just
failed rotates to the back instead of being retried first. Tier 1 exists because
`POST /proxies/reset-health` wipes every verdict — on 2026-08-24 one click emptied tier 0
across all 21,600 rows and left a single tier ordered NULLS FIRST, i.e. *never-used sessions
first*, the opposite of the intent.

> **Caveat (see `CONFIRMED_FACTS.md` §16):** the measurement originally justifying tiers 1-vs-2
> was invalidated by the tier-1 poisoning discovery. The ordering is currently a **HYPOTHESIS**.

Candidates are shuffled inside a bounded window (`_spread_window`, capped at pool/4) so
concurrent leasers do not all walk the same head of the queue. The window must stay a fraction
of the pool, or shuffling defeats the "just-failed rotates to the back" guarantee.

### Lease accounting

A **lost claim race** (someone committed first) is counted separately from a **failed health
probe**. Conflating them let a worker burn its whole probe budget on healthy candidates and
then report pool exhaustion — blaming the pool for contention. Confirmed live: 4 of 9 workers
stuck at READY naming five candidates that were all `is_healthy=True`.

Probes run **outside** any open transaction; only the winning candidate is re-locked
(`FOR UPDATE SKIP LOCKED`, single row). Holding a row lock across a multi-second network probe
would serialise a whole fleet launch against itself.

### Screening

**Tier-1 raw (primp) screening is DISABLED by default and must stay that way.** Raw-probing an
exit you intend to browse from takes it from 83% to 0% (`CONFIRMED_FACTS.md` §4). Read that
entry before re-enabling it.

## Webshare

| Property | Value |
|---|---|
| Endpoint | `p.webshare.io:80` — **identical for every credential we own** |
| Credential grammar | `{username}-{country}-{geo}-{session_id}:{password}` |
| Sticky | a **numeric** session-id suffix pins one exit |
| Rotating | the literal suffix `-rotate` gives a new IP per request |
| Geo | injected into the **username**: `sodade2026-17` → `sodade2026-DE-17` |
| Rotation mechanism | **change the session id** — no API call, no lease, no Hub round-trip |
| Sticky TTL (dashboard) | 24 h |
| Proxy Idle Timeout (dashboard) | 15 min |
| Actual observed bind stability | **can break in under 10 min while actively used** |

**The session id is the identity.** Because host:port is constant, identifying a webshare
proxy by its endpoint identifies nothing — every worker in every run logged the same string
until this was fixed. Logs now carry `proxy=p.webshare.io:80#51`.

**Rules:**
1. Hold the session id to keep an exit; change it to get a different one.
2. Any retry after a *transport* failure must change the id — retrying a dead tunnel cannot
   succeed. Wired into: both login transient paths, portal-unreachable, the reCAPTCHA
   IP-mismatch path, and `do_swap`'s retry.
3. **Never invent a session id.** `roll_sticky_session` returns the URL **unchanged** when it
   does not recognise a session id to roll. Appending one blindly rewrites the *username* — it
   authenticates against a suffix-parsing gateway and fails outright anywhere else (`u` would
   become `u-276569`). The caller falls back to a real proxy rotation.
4. A credential whose session id reads `rotate` is worth alarming on — it breaks every
   IP-bound session we hold.

**The hard constraint (`CONFIRMED_FACTS.md` §1):** a sticky exit can move *while in use*, well
inside the idle window. Nothing we control prevents this. Keepalive preserves the portal
session; it does **not** pin the exit. Design accordingly — treat "our IP moved" as a routine
event to detect and recover from, not an anomaly.

## SOAX

| Property | Value |
|---|---|
| Endpoint | `proxy.soax.com:5000` |
| Credential grammar | `package-{id}-country-{cc}-sessionid-{sid}-sessionlength-{n}` |
| Sticky | `sessionid` segment, bounded by `sessionlength` (3600 s for us) |
| Geo | a **parameter**: `package-335959-country-de-...` |
| Idle release | exit released after `idlettl` of silence |
| Extra failure mode | residential exits simply go offline |
| Rotation mechanism | replace the `sessionid-<x>` segment |

**Status: country-fr is burned** — DataDome ASN block after 488 IPs.

SOAX has a *third* way to lose an exit that webshare does not: the underlying residential IP
can drop off the network entirely, independent of any timer.

## Failure semantics (both providers)

| Symptom | Meaning | Correct response |
|---|---|---|
| `ERR_TUNNEL_CONNECTION_FAILED` / `ERR_CONNECTION_CLOSED` / `ERR_TIMED_OUT` | this exit is dead | **roll the session id** — never retry the same one |
| `Por favor, confirma o reCAPTCHA` | token minted on one IP, sent from another — **our exit moved** | roll; do **not** charge the sub-account's strike budget |
| Schedule.jsp loses its markers | often the same IP move | re-warm; check the exit before blaming form state |
| Submit refused | often the same IP move | re-warm; check the exit |
| `chrome-error://` page | failed navigation, now an opaque origin | re-anchor by **navigation** before any in-page fetch |

**One event, three portal symptoms.** Before `exit_ip.py` existed, nothing in this codebase
ever looked at its own exit address, and a single IP move was diagnosed as three different
portal problems — then "recovered" by re-warming or re-logging in *from the new IP*, which is
why those recoveries so rarely worked.

**Charging our own rotation to the account budget burned 3/3 and 2/2 sub-accounts** before
the IP-mismatch check was moved to sit beside `transient`, *before* `attempt += 1`.

`exit_changed()` is biased to False on purpose: a false positive costs a needless session
rebuild — a fresh login, a CAPTCHA solve, and a slice of the binding constraint — so an unknown
reading must never trigger one.

## Standing operator instruction

**Do not attribute failures to proxy quality.** Webshare works for login, warmup and slot
detection. When applying fails while those succeed, the cause is in our own browsing/session
handling, not the proxy. This instruction has been correct every time it was tested — it
caught three separate misdiagnoses.

The measured exception, recorded for completeness: a *dead exit* is real and is fixed by
rolling the session id, not by blaming the pool. That is a transport fact, not a quality
judgement about the provider.

## soax parameter contract (analysed 2026-08-25)

Our credentials are generated by `scripts/gen_proxy_pool.py` as
`package-{PKG}-country-{cc}-sessionid-{16 random}-sessionlength-{LEN}-bindttl-{T}-idlettl-{T}-opt-wb`.

**Construction moved to `libs/proxies/credentials.py` (Phase 3, 2026-08-26, `DECISIONS.md` D33)** —
`build_soax_credential`, `build_webshare_credential`, `soax_session_id`. `scripts/gen_proxy_pool.py`
is now a thin CLI wrapper (argparse + per-country count splitting) around the same functions
`libs/proxies` exports for reuse elsewhere. The grammar itself, and every value below, is
unchanged — golden-sample tests (`tests/proxies/test_credentials.py`) pin the exact pre-relocation
output format so a future refactor of the builders cannot silently drift it.

| parameter | meaning | our value | basis |
|---|---|---|---|
| `sessionlength` | how long the session id may hold one exit | **3600** | **no recorded justification** |
| `bindttl` | how long soax keeps re-binding the SAME exit after it drops | 600 | measured; reverted from 5 on 2026-08-22 |
| `idlettl` | how long a node stays bound with NO traffic | 900 | measured 2026-08-21 |

**All three are OUR values, not provider requirements.**

`bindttl` and `idlettl` each carry a detailed, measurement-backed comment explaining the exact
value. **`sessionlength = 3600` carries none.** It sits under a generic "non-secret defaults
confirmed working as of 2026-08-13" header and entered the repo wholesale in the single Phase-2
reconstruction commit (`e273ef9`) — never separately introduced, justified, or measured.

Interaction: `idlettl` releases an exit for *silence*; `bindttl` governs re-binding after a *drop*;
`sessionlength` is a **hard ceiling that overrides both**. Q1 measured it directly — 20/20 sessions
changed at 60.2–63.4 min under continuous 1/min traffic. No amount of traffic, and no `bindttl`
value, extends it.

**Whether soax supports a longer `sessionlength` is UNKNOWN** — not documented anywhere in this
repo, and not something to assume. That question, not the value itself, is the actionable item.

**What the provider guarantees about exit persistence: nothing we have in writing.** Every stability
property we rely on is inferred from our own measurements.

## What no provider here guarantees

Neither webshare nor soax offers us a contractual exit-persistence guarantee. Webshare exposes
*connection*-scoped controls (Session Timeout, Idle Timeout) which do not govern the session-id →
exit mapping our workers actually depend on — Q1 showed exits moving inside the idle window, and
showed connection reuse conferring no protection.

**The only configuration in this project's lineage with a real per-session exit guarantee is a
STATIC ISP proxy** — one IP per held session, which is what storm-auto migrates onto before holding
(`CONFIRMED_FACTS.md` §19). We own none.

### Named ISP pools — 2026-09-16 (`DECISIONS.md` D41)
A **pool is a name on a row** (`proxies.pool_name`, migration `cj000poolname`), not a table.
Importing under a new name creates the pool by definition; importing under an existing one appends.
There is no create step and no lifecycle. A `proxy_pools` table would buy referential integrity and
per-pool metadata we have no use for, at the cost of a join on the lease hot path and an
orphan-pool cleanup problem — revisit only when a pool needs attributes of its own (a cost, a
contract expiry, a vendor contact).

`NULL` means *belongs to no named pool*, and every pre-`cj000` row stays NULL. Unlike the geo
filter, **a pool filter does not admit NULL**: a booking that named its pools must never be handed
an unrelated ad-hoc import, because these are finite individually-owned IPs another booking may be
relying on. No filter at all still means "any pool", so every pre-existing caller is unaffected.

**Several pools per booking is the requirement, not a nicety.** An ISP purchase is a fixed number
of IPs — "10 from Thordata" — and that is routinely fewer than the worker count, so a booking draws
from the **union** of the pools it names. `PROXY_POOLS` / `HOLD_PROXY_POOLS` mirror
`PROXY_GEOS` / `HOLD_PROXY_GEOS` exactly: comma-separated, blank means all, one pair per phase — so
there is one filter idiom rather than two.

Both filters compose and neither overrides the other, and neither weakens **D33**: an unhealthy
*static* row stays excluded inside a named pool, because a static probe failure describes a real
resource (unlike a rotating one, D19). Dedup on `(endpoint, credentials_ref)` is **global, not
per-pool** — the same physical IP in two pools would be leased twice concurrently, and
one-worker-one-IP is the whole point of a static resource.

Capacity is reported as `leasable`, not `total` (`GET /proxies/isp-pools`). The operator's real
question when assigning pools is "do these cover my worker count?", and a deactivated or condemned
static row really is out of service. Pool exhaustion now names the pools searched, because with
finite pools that is the *expected* error once workers outnumber proxies and the next action is to
assign another pool or buy more.

### Two-tier health check, and what may be deleted — 2026-09-16 (`DECISIONS.md` D42)
| | tier 1 | tier 2 |
|---|---|---|
| question | can this proxy carry traffic at all? | can this IP reach the portal right now? |
| probe | raw request → **neutral** url (`api.ipify.org`) | real browser → the portal |
| cost | ~1 s, 16 in parallel | ~25 s, 4 in parallel |
| stored in | `is_healthy` / `health` | `portal_ok` / `portal_health` |
| gates selection? | **yes** (static rows, D33) | **never** |
| gates deletion? | **yes** | **never** |

**Tier 1 must not probe the portal, and this is the one rule that matters here.** `quick_screen`
does — it is a pre-lease negative filter and tolerable there — but a throttling portal produces
timeouts, `"timed out"` is a dead-marker, and the verdict then describes the portal. On 2026-08-28
that condemned 4,489 rows and stopped 73 of 120 workers launching; re-probed against a neutral url
the same rows connected 20/20. That was survivable when rows were regenerable strings. It is not
survivable now: tier 1 is what the delete button keys off, and an ISP proxy is a purchased,
individually-owned IP.

**Tier 2 is skipped when tier 1 fails** — not (only) to save ~25 s of Chromium, but because a
browser probe through a dead tunnel returns a portal-shaped error for a connectivity problem, which
is precisely the misattribution that has repeatedly sent investigations here the wrong way.

**Delete refuses three things**, and `force` is required to override any of them: a row with an
**active lease** (`proxy_leases.proxy_id` is a live FK — deleting through it is the non-JSON 500 that
the Detach button produced and that made `ci000droprot` fail on its first run); a row whose **tier 1
passed**; and a row that has **never been checked**, because absence of a verdict is not a verdict.
The unchecked test is evaluated *first*: `is_healthy` defaults to `True`, so an unprobed row would
otherwise be reported as "tier 1 passed", stating a verdict that never ran.

Selection is capped at 200 per run. One dashboard click must not be able to launch hundreds of
browsers — that is the shape of the 2026-09-15 incident where an inline probe saturated the
executor and took the Hub down. Probing also happens **outside** the DB session: the connection is
released before the probes and re-acquired to write, because holding a pooled connection across
tens of seconds of browser work is what produced the audit deadlock.
